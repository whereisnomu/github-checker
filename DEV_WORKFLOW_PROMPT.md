# Dev Workflow Prompt

## Context

Этот проект ведется через ветку `dev`.
Любые дальнейшие изменения нужно делать аккуратно и по git best practices.
Главная цель: каждая итерация работы должна быть воспроизводимой, понятной и готовой к ревью.

## Main Rules

1. Не работать напрямую в `main`.
2. Базовая ветка для интеграции изменений: `dev`.
3. Перед началом новой задачи:
   - убедиться, что локальный репозиторий в корректном состоянии;
   - перейти на нужную ветку;
   - не смешивать в одном изменении разные задачи.
4. Каждое логически завершенное изменение:
   - проверить локально;
   - оформить отдельным коммитом;
   - запушить;
   - создать PR в `dev`.
5. Не мержить PR без явного разрешения пользователя.

## Branch Strategy

- Постоянная интеграционная ветка: `dev`
- Рабочие ветки под задачи:
  - `codex/<short-task-name>`
  - пример: `codex/fix-openrouter-retries`

Если пользователь отдельно попросит работать прямо в `dev`, это допустимо, но по умолчанию лучше создавать task-ветку от `dev`.

## Standard Flow

1. Обновить локальный контекст:
   - проверить текущую ветку;
   - проверить `git status`;
   - при необходимости подтянуть актуальное состояние удаленных веток.
2. Переключиться на `dev` и убедиться, что она актуальна.
3. Создать новую рабочую ветку от `dev`.
4. Выполнить изменения.
5. Прогнать локальную проверку:
   - минимальные smoke checks;
   - компиляцию;
   - тесты, если они есть.
6. Посмотреть diff.
7. Сделать осмысленный коммит.
8. Запушить ветку.
9. Создать PR с base = `dev`.
10. Сообщить пользователю:
   - что изменено;
   - как называется ветка;
   - какой коммит создан;
   - что PR направлен в `dev`.

## Commit Rules

- Один коммит = одна логическая единица изменений.
- Не делать “мусорные” коммиты вроде:
  - `fix`
  - `changes`
  - `update`
- Формат коммитов:
  - `feat: ...`
  - `fix: ...`
  - `refactor: ...`
  - `docs: ...`
  - `chore: ...`
  - `test: ...`

Примеры:

- `fix: stabilize openrouter retry handling`
- `docs: add dev workflow prompt`
- `refactor: clean post-filter for ai review`

## Pull Request Rules

Для каждого PR:

- base branch: `dev`
- title: короткий и понятный
- body должен содержать:
  - что сделано;
  - как проверено;
  - возможные риски или ограничения.

Не выполнять merge, squash merge или rebase merge без прямой команды пользователя.

## Safety Rules

- Не удалять и не переписывать чужие изменения без явного разрешения.
- Не делать `git reset --hard`, `git checkout --`, `git clean -fd` без прямого запроса пользователя.
- Если рабочее дерево грязное, сначала понять, какие изменения относятся к текущей задаче, а какие нет.
- Если что-то выглядит конфликтующим или подозрительным, остановиться и явно отметить риск.

## Session Reminder

Перед любой новой задачей сначала вспомнить:

- работаем через `dev`;
- изменения оформляем отдельной рабочей веткой;
- каждый законченный кусок работы коммитим;
- пушим ветку;
- создаем PR в `dev`;
- merge только после явной команды пользователя.

## Immediate Next Step

После создания этой инструкции следующий шаг:

1. создать ветку `dev`, если ее еще нет;
2. перейти на workflow через `dev` и task-ветки;
3. дальше все изменения вести уже по этой схеме.
